## 摘要

面向2026 FPGA竞赛赛题二，本设计提出由RISC-V处理器负责场景管理、FPGA协处理器负责二维矩形绘制的软硬件协同架构。系统采用256位命令描述符与RGB565像素格式，实现矩形填充、块复制、全局Alpha混合和颜色键去背。渲染数据路径复用同步行RAM完成源行缓存与结果暂存，通过行内burst、带owner的仲裁和写响应确认管理访存顺序；控制侧提供AXI4-Lite寄存器接口，存储侧提供AXI4适配器，显示侧配置帧缓冲读取、双缓冲换页与光栅时序。现有十项定向功能仿真均记录PASS，覆盖命令、渲染、总线及显示相关路径。Vivado对Artix-7的代理综合结果为系统框架占用3680个LUT、3840个触发器、2块RAMB36和1块RAMB18，该结果仅用于RTL资源结构评估。真实Sapphire、DDR3、PLL与HDMI接口、多时钟交接和应用软件仍需集成，目标Ti60资源、时序、加速比及稳定60 FPS负载边界尚待实板验证。报告给出当前实现、验证边界与后续评价方案，为完整系统搭建提供依据。

## 1 设计任务与平台约束

### 1.1 赛题目标与基础功能

二维游戏和图形界面的画面更新可以分解为背景填充、矩形图像搬移以及精灵叠加等操作。对于这些反复作用于像素阵列的任务，赛题二要求由 RISC-V 承担游戏或界面控制，并将矩形渲染交给 FPGA 协处理器执行。《2026 FPGA竞赛赛题指南 -8.22(更正版)》将 AXI4 总线、DDR3 帧缓冲和 HDMI 显示列入目标系统，因而本设计的对象不仅是像素运算单元，还包括从处理器提交命令到帧缓冲更新、显示输出的完整通路。本文据此采用处理器控制、硬件执行矩形操作的系统划分，将运算正确性与存储、显示接口的可集成性共同作为设计约束。[R1]

基础渲染功能为 Solid Fill 和 Block Copy。前者向目标矩形写入指定颜色，后者依据源地址、目标地址、宽度和高度完成图块搬移；命令入口需要使软件能够表达这些参数，并获得操作完成状态。更正版同时要求使用突发传输与 FIFO，因此不能仅以逐像素运算结果正确作为功能链路的全部依据。矩形数据在 DDR3 中的连续访问、内部缓存对存储停顿的吸收，以及渲染与显示读取共用外存时的事务组织，都属于实现基础要求所需的工程内容。现有系统围绕命令队列、行级读写和显示预取组织 RTL，其具体输入输出关系在后续架构章节展开。[R1][R7]

显示端的基础目标为 HDMI 输出至少达到 640×480、60 Hz，并采用双缓冲减少渲染过程对当前显示画面的干扰。双缓冲要求的不只是分配两块存储空间，还需要规定处理器和渲染器何时访问后台页、何时确认写回完成，以及显示端何时切换前台页。赛题还要求在屏幕上实时对比纯软件 CPU 渲染与硬件加速渲染的 FPS；这一对比属于基础展示内容，而非高阶扩展。显示扫描以 60 Hz 运行，并不自动证明每秒完成了 60 次新画面渲染，故报告分别使用显示刷新率与渲染帧率描述这两类指标。[R1]

### 1.2 高阶挑战与评价边界

高阶挑战在基础闭环之上增加 Alpha 混合、Color Key 透明色处理，以及面向高负载精灵场景的 60 FPS 演示。Alpha 需要按透明度组合前景和背景，Color Key 则根据指定透明色决定保留背景还是写入源像素；两者除运算语义外，还改变了存储访问需求。当前工程已包含相应像素功能与行级处理路径，但器件上的运算映射、外存竞争和软件调度仍影响其最终吞吐。因此，本报告将高阶算子的 RTL 实现与高负载演示结果分别评价，不由算子存在推导实板性能，也不把基础所需的突发传输、双缓冲或 FPS 对比作为额外完成的高阶项目。[R1][R7]

性能对比应建立在可对应的工作负载上。CPU 路径与硬件路径需要使用相同的画面尺寸、像素格式和矩形序列，并说明帧计时是否包含命令提交、完成等待及换页操作；否则，处理器执行时间与硬件内部周期数可能反映不同的工作范围。高负载精灵演示还需要固定精灵尺寸、数量和叠加方式，才能说明某个帧率对应的实际负载。上述口径是本文为落实赛题评价目标采用的测试约束，并非已取得的性能数据；屏上 CPU/硬件 FPS、加速比和稳定精灵负载均为【待补充：同场景板级性能测试及屏显结果】。[R1][R7]

### 1.3 目标平台与存储约束

目标平台按现有 Ti60F225 开发套件资料确定。已提供的参数截图标明 FPGA 为 Ti60F225I3，具有 60K LE 和 4 个独立 PLL；板载 DDR3 为 16 位数据宽度、256 MB 容量，资料所列最高速率为 800 Mbps，另有 8 MB QSPI Flash。[R2] 这些信息支持逻辑规模、外存容量和时钟资源的初步规划，但不是已完成的板级配置。本文不据截图推定尚未核实的 DSP、片上 RAM 总量或具体引脚连接；DDR3 速率标称值也不等同于应用可持续获得的有效带宽。实际控制器配置、时钟分配和物理接口约束为【待补充：与实物板卡一致的 BOM、原理图及生成 IP 参数】。

本实现选择 RGB565 作为帧缓冲和内部像素通路格式，每像素占 16 bit；这是当前工程的数据表示选择，不是将赛题限定为唯一像素格式。矩形宽度、高度以像素计，基地址和行跨度以字节计，因而第 y 行、第 x 列像素地址为 base＋y×stride＋2×x。对于无行尾填充的 640×480 画面，行跨度为 1280 B，单帧容量为 640×480×2＝614400 B，双缓冲共需 1228800 B，即 1.171875 MiB。这些数值由格式与尺寸直接计算，只描述帧缓冲占用，不包含精灵素材、处理器程序、软件工作区或对齐预留。[R7]

从帧缓冲容量看，两页 RGB565 画面所需空间小于截图标明的 DDR3 容量；系统是否能连续输出画面，仍取决于访问服务能否满足显示时限。显示端需要按固定光栅持续取得像素，渲染端则会随着矩形尺寸和算子类型产生不同的读写流量，外存刷新、仲裁及跨时钟传递还会引入停顿。由此，平台规划不能停留在“画面能够放入 DDR3”的容量判断，还必须落实 FIFO 深度、突发访问、帧页所有权以及系统时钟与像素时钟之间的交接。本文保留这些约束，并将理论容量与后续真实带宽、时序测量分开报告。[R2][R7]

### 1.4 当前实现范围与整机完成条件

当前 c2_renderer_system 是板卡无关的组装顶层，已连接命令入口、矩形渲染器、存储仲裁和显示路径，并提供可选择的 AXI4-Lite 控制适配与 AXI4 Full 存储适配。源码默认内部像素数据宽度为 16 bit，外部 AXI 数据宽度参数为 128 bit，系统同时启用行级读突发与写突发；这些参数描述已实现的通路形式，不指定最终 DDR3 IP 的用户接口配置。默认可仿真分支仍使用直接 CSR、行为内存和同源时钟，启用厂商接口分支也不意味着 Sapphire、DDR3 PHY、真实跨时钟电路或 HDMI PHY 已经生成并完成连接。[R7]

现有验证覆盖应按其配置解释：小尺寸行为模型回归用于检查命令、存储和显示控制的配合，AXI 系统壳的 NOP 测试用于检查控制入口，代理综合与结构映射用于观察特定配置下的逻辑实现。它们不构成 640×480@60 Hz 实板显示、真实 DDR3 访问或 CPU/硬件 FPS 对比的验收证据。完整系统仍需补齐 RISC-V 驱动与共享存储访问约定、Sapphire/DDR3/HDMI 及跨时钟集成、板级约束、布局布线与实板测试；其完成记录为【待补充：整机工程、软件演示及板级验收结果】。后续章节以这一边界区分已实现设计、已有验证和待完成工作。[R7]

## 2 系统总体架构与数据流

### 2.1 控制、存储与显示路径的分工

系统以矩形命令作为软件与硬件之间的工作边界。目标板级方案中，RISC-V 处理器负责组织图形对象、指定源图像和目的帧缓冲地址，并向二维渲染协处理器提交操作参数；协处理器将这些参数转换为像素运算和连续访存事务，把结果写回 DDR3。显示端独立读取当前显示页，在固定光栅时序下输出像素。因此，一条命令从提交到显示经历的是控制请求、存储处理和视频扫描三个阶段，命令已被接收、目的矩形已写回以及新页面已经显示，分别对应不同事件，不能由同一个忙状态或提交脉冲代替。[R3][R4][R6]

当前代码以 `c2_renderer_system` 组装这些板卡无关模块。其控制入口可选择直接 CSR 信号或 AXI4-Lite 从接口，渲染端与显示端通过内部存储仲裁器共享一个外存访问出口，视频端输出 RGB565 数据和同步信号。该模块是通用组装顶层（assembly top），不是可直接下载到开发板的板级顶层：它没有实例化完整的 Sapphire RISC-V 系统，也没有绑定 DDR3 物理引脚、PLL 或 HDMI 串行输出引脚。将已有逻辑放入板级工程时，需要在这一边界之外接入 CPU、系统互连和生成的外设 IP，而不能仅凭顶层端口展开就认定整机集成完成。[R7]

### 2.2 从 CPU 寄存器写入到矩形描述符

软件提交的对象是一条 256 位命令，内容包括操作码、像素格式、源地址、目的地址、矩形宽高、源与目的行跨度，以及填充颜色、Alpha 和颜色键参数。宽高以像素为单位，地址与行跨度以字节为单位；当前像素格式固定为 RGB565，每个像素占 2 字节。对矩形内部坐标 `(x,y)`，对应表面的访问地址为 `base + y × stride + 2 × x`。这一表示使连续行内像素与跨行间距可以分别处理，源图像和目的帧缓冲也不必具有相同的行跨度。[R3][R4]

在控制入口处，`c2_axi4lite_csr_adapter` 将总线访问转换为通用 CSR 握手，`c2_csr_cmd_bridge` 保存命令内容。软件依次写入字节偏移 `0x00` 至 `0x1c` 的八个 32 位命令寄存器，再写 `0x20` 提交寄存器；桥接器在提交被接受时锁存八个字的快照，形成独立于后续寄存器修改的命令包。提交端有一个待发送槽位，下游命令 FIFO 暂满时可以暂存一次提交；该槽位尚未释放时，新的提交访问受到背压。这样，较慢的寄存器控制访问与较长的矩形处理过程之间有明确的缓冲边界，软件仍需遵守总线握手，不能把连续写入次数直接视为已执行命令数。[R3][R5]

命令快照进入默认深度为 8 的 FIFO 后，由 `render_cmd_parser` 解码为结构化描述符。解析器检查操作码、RGB565 格式、非 NOP 命令的非零尺寸，以及所使用地址和行跨度的两字节对齐关系；有效描述符保持至引擎接收，非法命令被消费并产生错误事件而不进入像素处理。引擎还检查自身行缓存容量约束。控制面同时提供提交、接收、完成和错误相关计数，其中完成计数也会记录引擎以错误结束的命令，因此软件确认一次渲染成功时须结合错误状态，而不能仅观察完成计数增长。[R3][R4][R7]

### 2.3 从矩形描述符到行级像素结果

`render_cmd_mem_engine` 以矩形描述符为输入，根据操作类型决定是否读取外存。Solid Fill 直接生成指定颜色的目的像素，不需要读取源或背景；Block Copy 读取源行并写入目的行；Alpha Blend 和 Color Key Copy 都读取源行与目的位置原有的背景行，形成结果后写回完整目的行。颜色键路径在源像素等于键值时选择背景，否则选择源像素。当前实现通过完整背景行读取保留键值位置的原内容，并非以零写使能跳过这些位置；这一选择使各阶段保持连续行访问，但也使其具有背景读取流量。[R4]

行级处理使用一块共享同步行 RAM，而不是为源像素、背景像素与运算结果各配置一块完整缓存。源行读响应先写入 RAM；背景响应到达时，同步读出相同位置的源像素，完成混合或选择运算，再把结果覆盖回该位置。Block Copy 可以直接使用已经缓存的源行，Solid Fill 则在写数据阶段生成颜色。引擎在本行结果可用后发起写回，本行全部写段完成后按各自 stride 更新源和目的行基址，再处理下一行。这样的数据依赖将行 RAM 的使用阶段限定为源行保存、结果生成和结果输出，使缓存复用关系与状态机推进保持一致。[R4]

外存接口接收的是分段事务，而非完整矩形。渲染器依据当前行剩余像素数、最大突发长度和 4 KiB 边界共同确定下一段的长度，读源行、读背景行及写结果行均采用这一约束。内部数据宽度为 16 位，`req_len=N−1` 表示连续的 N 个像素拍；默认读写上限各为 16 拍，即一段最多携带 32 字节的像素数据，不能将其理解为 16 个 128 位 AXI 数据拍。行缓存容量与突发长度分别约束一行的暂存规模和一次存储事务的规模，二者在架构上承担不同职责。[R4][R7]

### 2.4 共享存储访问与写回完成边界

渲染引擎作为内部主设备 m0，显示读取器作为只读主设备 m1，两者接入 `c2_mem_arbiter_2m_owner`。仲裁器只在空闲时选择新的事务，并保存当前事务的归属；读响应返回发起该读事务的主设备，写事务则从描述符接受开始，跨越全部写数据拍，一直保持归属到写响应被原主设备接收。复位后的首次授权若遇到两路同时请求，可依据显示优先设置选择 m1，后续竞争采用轮转选择。该机制在没有内部事务 ID 的条件下隔离两路响应，同时使持续显示读取不会仅因固定优先级而永久阻挡渲染请求。[R4][R7]

仲裁后的 16 位存储流进入 `c2_mem_to_axi4_adapter`，再转换为参数化宽度的 AXI4 Full 主接口。默认 AXI 数据宽度为 128 位，适配器将连续像素聚合到对齐的宽数据拍中，利用首尾拍的字节写使能屏蔽请求范围之外的位置，并在读方向按请求的起始像素位置拆回 16 位数据。该适配器一次处理一个内部描述符，使用全宽递增突发，对跨越 4 KiB、像素未对齐或需要超过 256 个 AXI 拍的请求执行本地拒绝。它承担协议与数据宽度转换，不包含 DDR3 初始化训练、刷新控制或物理层。外存分支只有在 `ext_mem_init_done` 有效且 `ext_mem_init_error` 无效时才允许新描述符握手。[R5][R7]

目的像素送入写数据通道并不立即构成命令完成。引擎发送一个写段的末拍后进入写响应等待状态，AXI 适配器将 B 通道响应映射为内部 `wr_rsp`，仲裁器再将该响应交回渲染引擎；正常路径上，矩形末行的末个写段收到成功响应后，才产生成功完成事件。这里的完成边界是外存控制器接口对写事务的响应，不包含 CPU 缓存自动维护，也不意味着页面已被显示端切入。写错误会作为错误完成向上返回，软件不能在检测到错误后仍将该页面作为已完成画面提交。[R3][R4][R5]

内部 m0/m1 仲裁并不覆盖 CPU 的 DDR3 访问。若 Sapphire 需要向 DDR3 装载素材、直接绘制 CPU 基准画面或读取帧缓冲，则 CPU 的 AXI 主接口与本系统的 `m_axi_*` 主接口之间还需要外部系统级 AXI 互连，再由互连接入 DDR3 控制器从接口；不能把两个主接口直接并接到同一组 DDR3 AXI 信号。控制寄存器窗口还需要板级地址译码，CPU 仅提供 AXI4 Full 访问时，应按生成系统的接口条件加入 Full-to-Lite 桥接。当前代码提供的是加速器控制从接口和存储主接口，不包含这些 CPU 系统连接。[R7]

### 2.5 从写后页面到固定光栅输出

双缓冲以显示页和待绘制页分离读写对象。软件应向非显示页发出渲染命令，在相关命令成功完成后通过 `PAGE_REQUEST` 请求切页；页请求与渲染完成在 RTL 中是独立路径，页控制器不会代替软件判断一页是否已经画完。在系统连接中，`c2_page_flip_ctrl` 的提交触发端接到 `vblank_start`，而非有效显示区域的起始像素。待处理页面在垂直消隐开始时成为新显示页，显示基地址随之从 `PAGE0_BASE` 或 `PAGE1_BASE` 选出，避免在当前有效画面中途改变读取页面。[R3][R6][R7]

页提交后，时序发生器将预取事件延迟一个像素时钟发出，使 `c2_display_path` 捕获已经更新的页面基址、行跨度和尺寸，并清空旧 FIFO 内容；读取器就绪时，再在后续周期启动矩形预取。显示读取器通过同一外存出口获取当前页数据，返回像素进入默认深度为 1024 的行 FIFO，并在有效显示阶段按光栅消耗。到下一帧有效区域开始时，只有 FIFO 已有数据才使能该帧消费；复位后的首帧没有此前的消隐预取阶段，因而有意保持黑屏，避免从中途到达的数据开始显示半幅或错位画面。[R6][R7]

显示链的输出包括 RGB565 像素以及 `de`、`hsync`、`vsync`，其扫描节奏由视频时序发生器决定，不能随存储访问或接收端背压任意暂停。有效显示期间若 FIFO 耗尽，或视频物理层撤销像素就绪信号，当前逻辑会记录显示错误。因此，行 FIFO 的作用是吸收一定范围内的访存停顿，而不是保证任意 DDR3 延迟下均无缺像素。默认有效区域为 640×480，实际刷新率仍取决于板级像素时钟；HDMI TX/PHY 的像素接收、数据与同步延迟、串行化及物理引脚连接需在真实板级实现中验证。[R6][R7]

## 3 二维渲染协处理器RTL设计

### 3.1 矩形命令的表示与提交

二维渲染协处理器把一条矩形命令转换为有序的源数据读取、像素运算和目的数据写回。当前系统采用固定的256位命令表示，CPU不逐像素驱动运算器，而是给出操作类型、两个表面的起始地址、宽高与行跨度，由硬件维护行内位置和行基址。这一划分把软件工作集中在矩形组织与存储所有权管理上，同时把像素寻址和连续访存交给状态机。系统内实际数据路径固定为16位RGB565，地址与stride均以字节为单位，width和height以像素为单位；若矩形左上角已由软件折算到起始地址，则像素坐标与地址的关系为下式。[R3][R4]

$$
A_s(x,y)=A_{s0}+yS_s+2x,\qquad A_d(x,y)=A_{d0}+yS_d+2x.
$$

其中，源与目的可以采用不同的行跨度，因此矩形宽度不必等于整个帧缓冲的行宽。命令不包含独立的屏幕坐标或裁剪窗口；越过可见区域的处理必须在形成命令之前完成。`renderer_pkg.sv`给出了统一的打包顺序，解析器按相同位段提取字段，使软件提交、RTL解析与测试平台可以围绕同一份命令ABI建立对照。表3-1列出参与当前路径的字段及保留位，颜色填充只使用32位`color`字段的低16位。[R3]

表3-1 256位矩形命令的字段映射

| 位段 | 字段 | 当前含义 |
|---|---|---|
| [2:0] | op | 0为NOP，1为Fill，2为Copy，3为Alpha，4为Color Key |
| [10:3] | flags | 保留控制提示，当前不决定算子启用 |
| [12:11] | pixel_fmt | 当前仅接受0，即RGB565 |
| [15:13] | reserved_lo | 保留位 |
| [47:16]、[79:48] | src_addr、dst_addr | 32位字节地址 |
| [95:80]、[111:96] | width、height | 16位矩形宽度与高度 |
| [127:112]、[143:128] | src_stride_bytes、dst_stride_bytes | 16位源、目的行跨度 |
| [175:144] | color | Fill采用低16位RGB565常量 |
| [183:176]、[199:184] | alpha、color_key | 8位统一透明度、16位精确匹配颜色键 |
| [255:200] | reserved_hi | 保留位 |

控制桥使用八个32位命令寄存器构成256位快照，在`CMD_SUBMIT`写入被接受时保存整条命令，再通过ready/valid接口交给命令FIFO。因而软件改写下一条命令的工作寄存器不会改动已经提交的快照。保留的`flags[0]`和`flags[1]`仅表示未来ABI的有效性提示，当前由`op`直接选择Alpha或Color Key；即使这些提示位为0，对应操作仍会使用`alpha`或`color_key`字段。保留位没有形成新的混合模式，也没有“设置两个flag便同时执行两种效果”的组合语义。[R3][R7]

### 3.2 命令排队、字段校验与执行边界

系统的实际顺序为提交快照、原始命令FIFO、字段解析器、存储执行引擎。默认FIFO深度为8，FIFO只在输入握手时写入、输出握手时移除；处于满状态时，如果同拍有一条命令出队，仍允许新命令入队。解析器的输出是一个独立的弹性描述符槽，未被引擎接受时保持字段稳定；正在输出的描述符被消费时，可以同拍接收下一条原始命令。因此，命令缓存吸收的是控制面与执行面之间的速率差，而不是使多个矩形同时执行。引擎仅在空闲状态拉高`desc_ready`，一条命令的行读、计算和写回按既定顺序完成。[R3][R7]

解析器按照操作码、像素格式、尺寸、stride和地址对齐的顺序检查输入，多个字段同时错误时报告优先级靠前的错误。未知操作码和非RGB565格式被拒绝；非NOP命令的宽高必须非零，目的stride必须为偶数且至少为`width×2`，需要读取源表面的Copy、Alpha和Color Key还须满足同样的源stride约束。所有实际使用的像素基址均须按2字节对齐，Fill不使用源表面，因此不检查其源地址和源stride；NOP不检查未使用的尺寸、stride或表面地址，但仍受操作码和像素格式校验约束。用于比较最小stride的中间量保留17位，避免直接把16位宽度乘2后截断而误接收错误描述符。[R3]

校验失败的原始命令会被解析器消费，产生一个周期的`error_valid`以及对应错误码和序号，不再送往执行引擎。合法描述符进入引擎时还会重复必要的字段检查，以覆盖单元测试或其他调用方绕过解析器的情况。使用行缓存的Copy、Alpha和Color Key在burst模式下进一步要求`width≤LINE_BUFFER_PIXELS`，系统默认上限为4096像素；Fill直接生成常量写数据，不使用行RAM，因此不受这一容量条件限制，但仍须满足非零尺寸、有效stride和地址对齐。入口校验和引擎防御性校验均在发出访存请求之前完成，却不构成帧缓冲地址空间保护：当前代码没有根据DDR容量或页范围检查整个矩形，也没有检查全部地址递增是否溢出，合法表面边界仍由软件保证。[R3][R4]

### 3.3 RGB565像素运算的实际实现

执行引擎从一行的数据需求出发选择工作路径。Fill无需任何像素读请求，写数据通道重复输出`color[15:0]`；Copy先读完整源行到行RAM，再将该行写到目的地址；Alpha和Color Key在源行读取结束后，还要读取目的位置当前保存的背景行。表3-2中的读写量按一行宽度为W计算，仅表示当前算法的有效载荷，不包含总线对齐、握手停顿、DDR刷新或读写切换开销。相同的矩形命令因算子不同而具有不同的外存流量，这一差别来自运算语义和行级实现，并非CPU提交次数的差异。[R4]

表3-2 系统burst路径的逐行处理关系

| 操作 | 源行读取 | 背景行读取 | 目的行输出 | 一行有效载荷 |
|---|---|---|---|---|
| NOP | 无 | 无 | 无 | 0 |
| Fill | 无 | 无 | 重复填充常量 | 2W字节 |
| Copy | W像素 | 无 | 源像素原值 | 4W字节 |
| Alpha | W像素 | W像素 | 前景与背景逐通道混合 | 6W字节 |
| Color Key | W像素 | W像素 | 命中保留背景，否则复制源 | 6W字节 |

Alpha使用命令中同一个8位系数处理整个矩形，没有独立的逐像素Alpha平面。计算直接作用于RGB565的原生通道值，即红、蓝为5位，绿为6位，不先扩展成RGB888再回量化。对通道c，设前景为F_c、背景为B_c、通道上限为M_c，当前`blend565`函数沿用参考算子的`+128`偏置整数舍入，并对结果作上限饱和：[R4]

$$
O_c=\min\left(M_c,\left\lfloor\frac{F_c\alpha+B_c(255-\alpha)+128}{255}\right\rfloor\right),\qquad (M_R,M_G,M_B)=(31,63,31).
$$

这一表达式规定了可逐像素核对的整数结果：`alpha=0`输出背景，`alpha=255`输出前景。端点改变的是像素数值，当前状态机并未因端点而跳过源行或背景行读取。除数255与偏置128属于现有数值语义，后续若使用乘法分解、查找表或移位近似优化，必须检查是否仍保持相同输出，不能只凭视觉相近便替换为除以256。`rtl/ops`中的独立像素算子提供了参考语义，但当前存储引擎没有直接实例化这些流式模块；实际计算是引擎内部的组合函数，行级调度和背压由引擎状态机承担。因此，独立算子存在ready/valid封装，并不能作为整条渲染路径已经形成多级DSP流水线的依据。[R4][R7]

Color Key采用16位源像素与`color_key`的精确相等比较。命中时把对应背景像素作为结果，未命中时保留源像素，既没有颜色容差，也没有Alpha混合。当前系统启用源行和背景行burst，即使一行中只有少数像素命中颜色键，也会读取完整背景行，再写回完整目的行；透明像素在写回时携带的是原背景值，并非通过取消该像素的写使能来跳过。该选择增加了背景读取量，却保持了读、写描述符的连续结构。引擎保留的旧单像素路径中存在命中跳写或按需读取背景的分支，那些分支不代表系统当前的Color Key带宽模型；两个独立操作码也不提供一次命令融合Key与Alpha的能力。[R4][R7]

### 3.4 源行与结果共享的同步行RAM

行缓存采用一个逻辑上的简单双口同步RAM，允许每周期一次可选写入和一次带寄存器输出的读取。默认组织为4096×16位，原始容量为65536 bit。Copy将每个源响应按行内索引写入RAM；Alpha和Color Key则先将完整源行存入相同数组，随后利用背景响应触发源像素读取，并把计算结果覆盖回原位置。因而源数据与结果数据在不同阶段共享存储空间，无需为前景、背景和输出各设置一块完整行RAM。这里的“一块”指RTL中的逻辑存储数组，不表示目标器件综合后必然只使用一个物理嵌入式存储块。[R4]

同步读取具有一个周期的延迟，背景数据不能在响应到达的同拍直接与尚未读出的源像素配对。引擎在接受背景响应时，把背景值和索引保存在`dst_pipe_data_q`、`dst_pipe_index_q`中，同时启动对应位置的RAM读取；下一拍由`dst_pipe_valid_q`指示这对数据有效，将混合或颜色键选择结果写回。连续背景响应可以依次推动这一短流水，而响应间出现停顿时，有效标志会阻止无效数据写入。每个背景读段的末拍之后进入`ST_LINE_READ_DST_DRAIN`，确保该拍结果已经覆盖到RAM，再启动下一读段或行写回，避免在同步写尚未生效时取走旧源像素。[R4]

RAM数组和读取输出寄存器放在不带复位的时钟进程中，控制寄存器与状态机则使用复位。这样不需要为整行内容生成复位逻辑，便于综合工具识别同步RAM结构；数据有效性来自访问顺序，即非Fill操作必须先填入本行有效数据，随后才允许写回读取。写描述符握手所在周期用于预取该段第一个像素，写数据每成功握手一拍才读取下一个像素。当下游撤销`mem_wr_ready`时，RAM读使能停止推进，输出寄存器、段内索引与`mem_wr_last`保持对应关系，避免因存储背压造成像素重复或漏写。[R4]

### 3.5 行级burst生成与4 KiB边界拆分

系统组装层显式启用`READ_BURST_ENABLE=1`和`WRITE_BURST_ENABLE=1`，而独立引擎模块的默认值仍为0，以兼容早期单拍测试。报告中的行级描述符、共享行RAM和提交响应均以系统启用的burst路径为准。内部存储接口每拍为16位，因此默认`MAX_READ_BEATS=MAX_WRITE_BEATS=16`表示至多16个RGB565像素、32字节有效载荷，并不是16个128位AXI数据拍。读写各段均只维护一个未完成描述符，读段响应结束或写段提交响应到达后，才推进到下一段。[R4][R7]

对行内起始索引i、矩形宽度W和该段字节地址A，分段长度同时受剩余像素数、配置最大拍数M及距离边界的可用字节数限制。当前读写边界均为B=4096字节，像素为2字节，段长度N按下式生成；地址预先满足2字节对齐，因此边界余量可表示为整数拍数。[R4]

$$
N=\min\left(W-i,\ M,\ \frac{B-(A\bmod B)}{2}\right),\qquad \texttt{req\_len}=N-1.
$$

例如，一段从`0x0FF8`开始且行内仍有足够像素时，到`0x1000`边界只剩8字节，即使最大拍数为16，该段也只能包含4个内部像素拍。后续段从`0x1000`继续，再按剩余长度和最大拍数计算。源行与背景行各自依据本表面的基址拆分，不要求二者具有相同的段边界；写回同样依据目的基址独立拆分。该方式保持每个描述符连续，又避免单段跨越4 KiB边界，宽总线适配层只需处理已经划定范围的像素序列。[R4]

读段被接受后，引擎保存预计拍数并逐拍比较`mem_rsp_last`与本段预计末拍。源行所有段结束后，Copy进入行写阶段，Alpha和Color Key进入背景行读取；整行计算结束后，目的行再分成若干写段。每个写段的`mem_req_*`仅承载地址、长度与方向，原单拍接口中的`mem_req_wdata`和`mem_req_wstrb`置零，真正的像素载荷通过独立的`mem_wr_*`通道发送。这种分离避免下游把描述符中的旧数据字段误当作第一个写像素。行内索引按成功提交的段长度递增，整行成功提交后才令行号加1，并把源、目的行基址分别增加各自stride。[R4]

### 3.6 写提交响应与存储owner生命周期

一行像素已经计算出来或末拍写数据已经被接收，都不足以表示该行完成了存储提交。引擎在`mem_wr_last`对应数据拍握手后进入`ST_LINE_WRITE_RSP`，等待该描述符唯一的`mem_wr_rsp`；只有响应成功，才开始下一写段、下一行，或对整条命令发出成功完成事件。若写数据阶段发生错误，引擎记录`burst_error_seen`，同样先进入响应等待状态，再结合提交响应的错误标志报告失败。由此，命令成功完成的边界被放在目的矩形末行末段的成功写响应，而不是数据离开行RAM的时刻。[R4]

渲染与显示共用存储访问端口，`c2_mem_arbiter_2m_owner`用事务所有者owner把描述符、数据和响应绑定在一起。默认渲染器为m0，显示读取器为m1；仲裁器仅在空闲状态选择新描述符，在owner有效期间阻塞另一主设备的请求，并仅向所有者使能对应响应的valid信号。已向下游呈现但尚未握手的描述符会锁住所选来源，不能因另一主设备随后到达而改变地址与长度。当尚无历史授权且两个请求同时到达时，可由`display_priority`选择显示；已有授权后的竞争按轮转状态处理，防止持续显示请求在事务边界上永久压制渲染请求。这种规则不提供帧级或整条渲染命令级独占，显示可以在相邻存储段之间获得服务。[R4]

读owner在正常读响应末拍握手后释放；写owner则从描述符握手开始，跨越全部写数据拍和等待提交响应的阶段，直到同一个主设备接受`wr_rsp`才释放。即使`wr_last`提前出现、在预计末拍缺失或数据拍带错误，仲裁器也只是结束写数据阶段并记录协议错误，不会直接把owner转交给另一主设备。该约束要求下游对每个已接受的写描述符产生且只产生一个写响应，并在上游不ready时保持响应。owner轮转的公平性以当前事务能够终止为前提；现有引擎和仲裁器没有响应超时计时器，下游不返回提交响应时仍会一直等待。[R4]

### 3.7 异常可观测性与功能限制

读响应错误以及实际末拍标志与预计长度不一致，会使引擎终止当前命令并输出`done_error`；仲裁器在错误读拍、显式末拍或预计长度边界释放读owner，防止引擎停止接收后共享端口仍等待它继续消费。这里的抽象层终止不意味着仲裁器能够排空任意外部总线长尾：下游适配器仍须处理已经发出的物理总线事务，不能把前一事务剩余响应误交给新owner。写异常保留提交响应闭环，读异常采用终止语义，两者不同的收束方式来自接口责任划分，而不是把所有错误统一退回空闲就能保证恢复。[R4][R7]

统计量用于定位命令与访存停顿，但各自的事件口径需要区分。解析器的`accepted_count`统计其消费的原始命令，包含随后被字段校验丢弃的命令；`completed_count`统计引擎返回的全部完成事件，包含正常完成和错误完成。名为`memory_error_count`的计数器实际上在`done_error`有效时增加，因此也可能包含引擎防御性描述符检查产生的错误，不能直接等同于DDR硬件故障次数。引擎的`request_count`按描述符握手增加，而非按像素或外部AXI拍增加；`pixel_count`表示已处理像素，Copy在接收源像素时计数，Alpha与Color Key在结果覆盖行RAM时计数，Fill在写像素被接受时计数。因此，像素计数前进并不代表这些像素已经获得成功写提交响应。[R3][R4]

FIFO的`drop_count`还具有不同含义：代码在每个`in_valid && !in_ready`周期递增该计数，而提交桥可以持续保持同一条pending命令，直到FIFO接收。该值反映受阻的提交周期，不是严格的独立命令丢失条数；系统将其与解析器丢弃计数相加导出，软件不宜只用提交、接收、完成与丢弃计数作简单相减来推断成功率。对于一条指定命令，字段错误事件、引擎完成及错误状态应按其所在阶段理解；整帧可用于切页的判断还需要覆盖本帧所有命令的成功写回，而不能只观察像素计数达到预期。[R3][R7]

当前执行顺序为按行读取、按行写回，既不提供整条矩形命令的原子性，也不保证任意重叠Copy的`memmove`语义。后续行读取之前，前面行的目的数据可能已经提交；当源、目的区域存在跨行覆盖关系时，早期写入可能破坏尚未读取的源数据。访存错误发生时，已成功提交的行或写段不会自动撤销，失败命令也不能据此视为完全未执行。软件应提供无有害重叠的区域，或通过临时表面组织安全序列，并在错误后决定是否重绘目标页。旋转、缩放、负stride、自动裁剪、逐像素Alpha及融合Key与Alpha均不属于当前命令执行能力。上述限制界定了已实现RTL的适用范围；其在目标器件上的运算映射、时序与真实外存负载下的持续吞吐仍为【待补充：含真实存储接口的目标器件实现与实测结果】。[R3][R4][R7]

## 4 总线显示与软硬件协同设计

### 4.1 从寄存器访问到命令提交

控制面以一个完整的二维操作为提交单位，而不是由 CPU 逐像素触发计算。软件在 32 位 CSR 窗口中依次准备八个命令字，再写入提交寄存器；`c2_csr_cmd_bridge` 在该次 CSR 握手时把八个字拼接为 256 位快照，其中 `CMD_WORD0` 对应最低 32 位。后续对命令字寄存器的修改不会改变已经进入提交槽的快照，因此命令准备与下游队列接收在逻辑上得到分离。这里的地址均为窗口内字节偏移，CPU 可见基地址必须由实际 SoC 地址译码和 BSP 决定，现有 RTL 没有给出可直接用于板上程序的绝对地址。[R3][R11]

提交寄存器后设置一个待提交槽。当命令 FIFO 已满但该槽为空时，桥接器仍能接收一次提交，并保持命令内容和有效信号，直到 FIFO 完成握手；只有再次写向已占用的提交槽时，桥接器才对这次访问撤销 `csr_ready`。页面请求具有独立的单项缓冲槽，等待规则与命令提交相同。该缓冲减少了软件对 FIFO 瞬时状态的依赖，却没有增加渲染引擎的执行并行度，也没有把“寄存器写入成功”转换成“像素写回完成”。总线前端仍需服从共享 CSR 端口的排队关系，因而一个等待中的事件写会延迟其他已缓存访问的执行。[R3][R5]

表4-1 控制窗口的主要寄存器

| 窗口偏移 | 名称或字段 | 当前实现语义 |
|---|---|---|
| `0x00`—`0x1c`，间隔 4 字节 | `CMD_WORD0`—`CMD_WORD7` | 32 位命令暂存字，可读写；不因写入单个字而启动操作 |
| `0x20` | `CMD_SUBMIT` | 写入任意数据时提交八字快照；提交槽占用期间等待 |
| `0x24` | `STATUS` | 位 0 为命令 FIFO 满，位 1—3 为 parser、engine、display 忙，位 4 为显示欠载，位 5 为存储错误；位 6 为控制器换页待处理，位 7、8 分别为 CSR 命令槽和页面槽占用；位 15:9 为 FIFO 层级低 7 位 |
| `0x28` | `PAGE_REQUEST` | 取写数据的低 `PAGE_W` 位作为目标页，进入 CSR 页面请求槽 |
| `0x2c` | `PAGE_STATUS` | 低 `PAGE_W` 位为活动页，从位 8 起的 `PAGE_W` 位为待处理页，位 16 为控制器待处理标志 |
| `0x30`、`0x34`、`0x38`、`0x3c` | 接收、完成、执行错误、混合丢弃诊断计数 | 前三项分别计数 parser 消费、engine 完成和 engine 错误完成；`0x3c` 合并 parser 拒绝数与 FIFO 未握手周期数，不是严格的丢失命令数量 |
| `0x5c` | 最近 parser 错误 | 位 0 直接反映错误有效脉冲，位 7:4 为错误码，位 31:8 为序列号低 24 位；不是读清型错误寄存器 |

表中寄存器支持状态观察，但尚未形成完整的软件完成事件接口。接收计数包含 parser 接收到后判为非法的命令；完成计数包含带错误的完成事件。`0x3c` 的 FIFO 分量在每个 `in_valid && !in_ready` 周期都会增加，所以命令被正常背压保持时也可能增长，不能据此独断命令失败或计算成功率。最近错误寄存器的错误码与序列号可以保持，位 0 却不是供软件长期轮询的粘滞有效位。`0x58` 的存储响应计数连接仲裁器读响应拍计数，也不等价于 AXI 写响应 B 的数量。驱动需要把提交、接收、完成和成功区分为不同状态，并先厘清混合诊断量、错误事件和完成事件的可观察关系，再规定计数器差分、回绕及超时规则。【待补充：基于实际 BSP 的命令驱动、可观察完成/错误契约及恢复实现。】[R3][R7][R11]

### 4.2 AXI4-Lite 控制访问与背压

`c2_axi4lite_csr_adapter` 把 AXI4-Lite 的独立通道转换为一次一个的 CSR 访问。写地址 AW 和写数据 W 分别保存在独立寄存器中，允许任一通道先到达；只有两者齐备才构成可执行写请求。读地址 AR 具有单独缓冲，所以前端最多保留一个未完成读和一个未完成写，但共享 CSR 端口并不并行执行二者。当完整写请求和待读请求同时具备执行条件时，适配器优先处理写请求。该安排使提交地址与命令数据不会因 AW、W 到达顺序不同而错配，无需对主机施加地址和数据同拍到达的额外条件。[R5]

CSR 握手结束后，适配器将写响应 B 或读响应 R 登记到输出寄存器。若主机暂不接收，`BVALID`、`BRESP` 或 `RVALID`、`RDATA`、`RRESP` 保持，关联方向的新请求不能覆盖尚未取走的响应。软件须采用对齐的 32 位全字访问，前端对 `WSTRB=4'hf` 的写入执行 CSR 转发，对任何部分字节写在本地返回 `SLVERR`，且不修改寄存器；不能依赖字节写完成状态位更新。前端没有另行检查地址对齐，地址保护属性也未用于权限区分；未实现地址的读数为零、写入无作用，不会因此自动生成地址译码错误。上述行为是当前适配器的明确边界，系统级访问权限与地址窗口仍应由外层互连管理。[R3][R5]

### 4.3 RGB565 内部事务到宽 AXI4 突发

数据面保持内部 16 位 RGB565 拍，外部 AXI4 默认采用 128 位数据宽度。`c2_mem_to_axi4_adapter` 接收按字节寻址的描述符，`mem_req_len` 表示内部拍数减一，写数据由独立的 `mem_wr_*` 通道随后提供。适配器将连续内部拍打包到对齐的 AXI 宽拍中，读方向则缓存一个返回宽拍，再依次输出所请求的 16 位分量。这样，矩形引擎无需随 DDR 用户端口宽度改变像素 ABI；不过打包和拆分仍经过内部单拍通道，不能把 128 位外部接口直接解释为每周期完成八个像素的端到端处理能力。[R5][R7]

设内部每拍字节数为 $b$，AXI 每拍字节数为 $B$，请求地址为 $A$，内部拍数为 $N=\mathrm{len}+1$，则适配器使用的首地址、首拍分量位置与宽拍拍数为

$$
A_0=\left\lfloor\frac{A}{B}\right\rfloor B,\qquad
k=\left(\frac{A}{b}\right)\bmod\frac{B}{b},\qquad
M=\left\lceil\frac{k+N}{B/b}\right\rceil .
$$

在地址满足内部拍对齐的条件下，外部 `AWLEN` 或 `ARLEN` 取 $M-1$，`AWSIZE` 或 `ARSIZE` 取 $\log_2 B$，突发类型固定为 INCR，事务 ID 固定为零。写首拍和末拍中不属于请求范围的字节保持 `WSTRB=0`，因此无需为保持相邻像素而进行额外的读改写。读事务同样访问对齐全宽地址，但只向上游交付请求范围内的分量；这意味着底层帧缓冲分配和地址窗口必须容纳实际宽拍覆盖范围，不能仅按有效像素字节判断所有访问边界。地址未按内部拍对齐、转换结果超过 256 个 AXI 拍，或对齐后的突发跨越 4 KiB 时，适配器在本地拒绝描述符，不直接发出该 AXI 请求。[R5]

写数据通道的推进不等待 `AWREADY`。宽拍准备就绪后即可保持 `WVALID`，即使整个 W 突发先于 AW 被接收，适配器仍保存写地址，直到 AW 握手完成；只有地址与末个 W 拍均已完成，状态机才进入 B 响应等待。上游收到的 `mem_wr_rsp_valid` 由 B 响应之后的状态产生，并综合写流末拍不匹配、`BRESP` 错误位以及返回 ID 异常。因此渲染器等待写响应的意义是保留事务完成边界，不能在 W 末拍送出时就提前释放页面。它仍是单个未完成事务的实现，前一个事务结束前不会接受新描述符，吞吐受响应等待与内部宽度转换共同限制。[R5]

异常处理也必须保持通道边界。写流过早出现末拍时，适配器记录协议错误，并用零字节使能补齐已声明的 AXI 突发；本地拒绝写描述符时，则接收并丢弃对应内部写流，按实际末拍或声明拍数结束后返回错误。读方向检查 `RRESP`、返回 ID 和 `RLAST` 是否与预计位置一致，向上游报告终止错误后，若真实末拍尚未到达，会继续接收并丢弃后续 R 拍，直到观察到 `RLAST`。这些措施用于避免异常事务污染下一笔传输，但当前适配器没有超时计时器；从设备永久不响应或缺失末拍时，不能承诺自动恢复，系统仍需补充超时和复位恢复策略。[R5]

### 4.4 固定光栅与消隐期显示预取

显示链路以光栅时序为输出约束，不能把 DDR 的可变访问延迟直接传递给像素计数器。`c2_video_timing_gen` 的默认水平参数为有效区 640、前肩 16、同步宽度 96、后肩 48，垂直参数为 480、10、2、33，总计数为 800×525，行场同步默认低有效。计数器逐像素时钟前进，`de` 标记有效区，FIFO 空或 PHY 不就绪均不会暂停光栅。该模块只给出计数与同步关系，实际帧率还取决于所生成的像素时钟，不能凭默认计数值认定已经完成 640×480@60 Hz 的板级输出。[R6][R11]

`c2_display_path` 将帧缓冲基址、stride、宽度和高度交给矩形 burst reader，由 reader 按行取得像素并写入 line FIFO；FIFO 默认深度为 1024 个像素，默认单次显示请求上限为 16 个内部拍。该容量用于吸收访问时延，不是完整帧缓存。FIFO 采用同步存储读与寄存输出，并将行末标记随像素保存；当前显示出口按 `timing_de` 消耗数据，未使用行末标记去重新校准光栅位置。因此持续供数的要求不仅关乎平均带宽，也关乎服务间隔，真实 DDR 仲裁造成的最长等待仍需在板级负载下验证。[R6][R7]

页面提交与预取采用分拍顺序。系统把 page controller 名为 `frame_start` 的输入实际连接到 `timing_vblank_start`，即有效区结束后的垂直消隐起点；时序发生器在其后一拍给出 `prefetch_start`。显示路径在该拍捕获已经更新的页面配置并清空 FIFO，待 reader 可以启动时再发出启动事件，同时再次清空 FIFO，阻止拖入消隐期的旧页迟到数据遗留到新预取流中。配置捕获和 reader 启动因此分开，既保证新页基址已生效，也为同步 FIFO 的清空保留顺序。[R6][R7]

在下一次有效帧起点，显示路径仅当 FIFO 已有数据时开启整帧消费；复位后的第一帧没有经历预取消隐期，设计允许其保持黑屏，而不在帧中途因数据到达突然开启图像。经历预取后仍空的帧会被记录为欠载。已开启帧若中途断粮，输出数据回退为零，光栅继续运行并记录错误；该行为保住同步时序，却不能作为欠载后像素位置正确的证明。`phy_pixel_ready` 在有效视频期间拉低也会形成错误，因为当前接口无法通过背压推迟真实屏幕像素周期。`display_pixel_count` 统计实际 FIFO 消费次数，`display_done` 来自 reader 结束而非屏幕显示结束，二者都不能直接充当可见帧率。[R6]

### 4.5 页面提交与软件所有权约定

`c2_page_flip_ctrl` 保存一个待处理页号，只在选定的消隐边界改变活动页。若边界到来时已有旧请求，控制器提交旧请求，同时可以接收一个新请求留待下一边界；若原本没有待处理请求，恰在边界到达的合法请求可当场提交。请求当前已活动的页面也会产生一次 `flip_ack` 脉冲，因此控制器的确认针对请求事件，而不只针对页号变化。CSR 页面槽和控制器待处理槽是前后两级状态，写入 `PAGE_REQUEST` 得到总线响应只表示前一级接收，不表示消隐提交已经发生；`PAGE_STATUS` 中的待处理页号也只有结合待处理标志才有意义。[R3][R6]

双缓冲的软件约定是将活动页视为显示所有，不向其发出新的渲染写入；CPU 或加速器在另一页完成绘制，核对每项命令的完成与错误，并确认没有未结束写响应后，再请求显示该页。该约定需要软件实施，现有混合诊断计数尚不能独立承担逐命令成功判定，page controller 也不读取渲染器忙状态或阻止命令中的目标地址覆盖活动页。控制器内部的 `flip_ack` 尚未映射为可读的提交计数器或中断状态，软件轮询只能使用现有活动页及两级待处理标志，不能假设存在一个未定义的换页完成寄存器。对重复请求同一页、多个请求并发或跨时钟状态观察，还需在驱动和状态接口中规定无歧义的确认方法。【待补充：页面状态机、请求串行化、换页确认和异常退出的软件实现。】[R3][R6][R7]

旧页回收还受显示读事务生命周期约束。如果上一帧 reader 拖入垂直消隐期，当前显示路径会先等待它结束，再启动新页 reader；活动页寄存器的变化本身并不证明旧页已经没有在途读请求。正常供数条件下，旧页读取应在本帧消费结束前完成，但欠载或异常恢复时不能仅凭页号变化立即复用旧页。可靠的软硬交接需要同时证明新页已提交和旧页读访问已结束，或在故障路径停止访问并重新建立所有权。当前未提供独立的旧页排空确认给软件。【待补充：旧页读事务排空的可观察条件、回收时序及异常场景验证。】[R6][R7]

### 4.6 CPU 共享存储、跨时钟与物理接口边界

CPU 软件绘图与硬件加速使用同一 DDR 帧缓冲，是实现同场景对比和资源共享所需的系统连接。当前内部仲裁器只接收渲染器和显示 reader 两个主端口，不包含 CPU；Sapphire 的内存访问与加速器 AXI4 master 仍需在外层互连汇合。若生成 SoC 只导出 AXI4 Full 控制访问，还需要相应协议桥接和地址译码，不能省略附加信号后当作 AXI4-Lite 直接相连。DDR 接入分支已用 `ext_mem_init_done` 且无 `ext_mem_init_error` 门控新描述符，初始化完成信号必须来自真实控制器校准结果，不能固定置位代替存储器训练。【待补充：Sapphire、CPU/加速器共享 DDR 互连、地址映射、DDR3 controller/PHY 端口与初始化联调。】[R7][R11]

帧缓冲可见性不仅由总线响应决定，也由 CPU 缓存属性决定。若 CPU 在可缓存区域生成源图像，向加速器交付前需要按实际平台完成脏数据写回与访问顺序约束；若 CPU 要读取加速器写回结果，则需避免继续使用旧缓存行。显示页提交也应发生在相关写入对显示主机可见之后，不能将一次普通变量赋值当成内存屏障。当前仓库没有完成这套 BSP 驱动，具体采用不可缓存映射还是 cache flush/invalidate，应依据实际 Sapphire 配置确定，不能提前假定 CPU 与加速器具备硬件缓存一致性。【待补充：帧缓冲映射属性、缓存维护函数、内存屏障及 CPU/硬件共享数据测试。】[R11]

当前可执行的默认路径令 system 与 pixel 使用同一输入时钟；启用时钟 IP 选项后，PLL/reset、页面 CDC 和显示存储 CDC 仍是替换用黑盒。页面跨域必须保持请求与页号一致，并使活动页、待处理页和标志在 CSR 域中一致采样；显示跨域必须保留每个描述符与全部返回拍的顺序、末拍和错误信息。现有 `c2_mem_cdc_blackbox` 仅预留显示只读通道，没有完整写数据和写响应端口，不能用作 CPU 或渲染器通用 AXI CDC。显示忙、欠载及计数器等像素域状态进入系统域后的同步或快照读取，也需纳入真实多时钟设计，而不是仅替换两个黑盒就视为完成。【待补充：时钟频率与约束、复位释放、页面/显示通道 CDC、状态计数器跨域与恢复验证。】[R7][R11]

HDMI 输出同样保留明确实现边界。现有 video PHY 黑盒只定义并行 RGB565 数据、有效区和同步信号的接点，没有生成 HDMI 编码、串行化、物理电气配置或板级引脚连接。板级 wrapper 需要依实际 TX/PHY 端口完成像素格式扩展，并使数据与 `de/hsync/vsync` 的流水延迟一致，同时满足有效区不可停顿的供数合同。当前总线、页面和显示 RTL 为后续集成提供了接口语义，但不构成真实 CPU、DDR3 与 HDMI 整机已经运行的证据。【待补充：HDMI TX/PHY、像素格式与延迟配置、PLL 和引脚约束、实屏输出与持续负载测试。】[R6][R7][R11]

## 5 验证方法与已有结果

### 5.1 验证层次与数据来源

当前验证围绕命令处理、像素读写、总线协议和显示交接四个层次展开。模块测试通过定向输入与期望输出比较，检查像素内容、地址分段、握手保持和错误计数；集成测试把渲染引擎、owner 仲裁器与行为内存连接，核对写入结果及完成响应；系统测试则观察命令提交、共享存储访问、垂直消隐换页和视频输出之间的关系。行为内存用于提供可控延迟和故障条件，并不包含 DDR3 控制器的训练、刷新、物理接口或真实时钟域行为，因此该层证据对应 RTL 功能和协议，不对应板级吞吐。[R8]

本章采用 2026 年 8 月 31 日保存在 `case2/tb/xsim_newguide_signoff_20260831` 的已有记录，工具日志标明 Vivado Simulator 2023.1，未在报告编写期间重新运行 EDA。该目录包含一次统一编译、11 次展开和 10 次功能仿真，共 22 个阶段状态文件；逐项记录均为 `state=completed`、`returncode=0`、`worker_in_job=false`，10 份功能仿真日志均有相应 PASS 标记。多出的一项展开属于无行为 IP stub，用于检查接口和生成分支，没有计为功能仿真。阶段退出状态与测试台自检结果同时核对，可以区分工具执行结束和断言通过，避免仅凭进程退出给出功能结论。[R8]

行级事务测试把突发长度和地址边界同时纳入检查。行读专项采用 `MAX_READ_BEATS=4`，将一条 10 像素源行放在 `0x0ff8`，要求依次按 4、4、2 个 RGB565 内部拍读取，并显式检查 `0x0ff8` 与 `0x1000` 两段描述符。行写专项把目的地址设为 `0x0ffe`，验证写请求在边界前后分成独立事务。这样的输入能够暴露“只限制长度、未处理地址边界”造成的错误；对 stride 则使用宽度允许但地址不对齐的两行命令，分别检查 parser 和绕过 parser 的引擎入口。NOP 不使用 surface，Fill 不使用源 surface，对这些未使用字段仍保留合法例外。[R8]

写完成的判断不仅依赖写数据是否全部握手。行写测试在数据末拍之后延迟返回完成响应，并在该响应上注入错误，要求命令最终表现为 `done_error`；集成测试再核对 `wr_rsp=10` 与 10 个写描述符一致，且结束时引擎和仲裁器均已释放忙状态。像素内容检查覆盖 3×2 Fill 与 Copy、Color Key 命中时保留原目的像素，以及 Alpha 的定点结果，例如前景 `0xf800`、背景 `0x001f`、Alpha 为 `0x80` 时得到 `0x800f`。这些是指定输入下的功能对照，尚不构成所有像素、几何尺寸及背压序列的穷尽证明。[R8]

AXI4 Full 的两种宽度测试均记录 `aw_waits_wvalid=1`、`aw_after_first_w=1`、`aw_after_last_w=1` 和 `w_before_aw=3`，说明测试确实命中了从机等待 WVALID 才给 AWREADY、首个 W 先于 AW、全部 W 完成后才接受 AW 的三类时序。读通道则分别注入 RID 不符、提前 RLAST 和延后 RLAST，要求抽象接口返回终止错误，并在需要时接收剩余物理拍直到真实末拍，再执行恢复读。日志中的 `protocol=5`、`axi=5` 以及读写错误计数是这些负向用例的预期结果。已有证据支持所列时序与恢复场景正确，尚无完整 AXI VIP 认证或与厂商 DDR3 IP 联合验证的结论。[R8]

### 5.3 系统扫描与接口 shell 的验证边界

系统扫描测试采用 4×2 有效区域、2 拍显示 burst 和同源时钟，行为内存预置两页不同像素。通过 CSR 提交一条 Fill 命令后，再请求切到 page1；测试等待垂直消隐提交，并对随后的完整有效帧逐位置检查 `video_valid` 和 `0x2000` 至 `0x2007` 的八个 RGB565 值，不允许把跨帧出现的有效样本拼为一帧。日志中的 `page1=8` 表示这一整帧核对完成，`video=16` 是测试期间累计有效视频样本，二者含义不同。结束检查还要求累计显示错误数、欠载指示及系统错误均为零。[R8]

该测试将垂直后沿设为 8 行，为串行行为内存和短 burst 留出足够预取时间；它验证的是换页、预取和扫描的衔接，不是实际 640×480 时序下的存储裕量测量。复位后首帧尚无前一垂直消隐触发的预取，显示路径按设计保持黑屏。真实系统中的 pixel clock、存储时钟、CDC、DDR 刷新和 PHY ready 行为仍可能改变最坏停顿条件，因此不能由这里的 `underflow=0` 推导出实板持续无欠载或 HDMI 已通过验收。[R7][R8]

AXI 系统 shell 使用 `USE_AXI4LITE_CSR=1`、`USE_EXT_MEM_IP=1`，该测试实例的 AXI 数据宽度为 64 bit，并将外存 `init_done` 保持为 0。八个全零命令字构成合法 NOP，经控制接口进入 FIFO、parser 和引擎后，提交计数与完成计数都变为 1；测试再通过 AXI4-Lite 读回完成计数。由于 NOP 不需要读取或写入帧缓冲，PASS 证明的是所选系统分支与控制通路能够工作，不是 AXI4 帧缓冲闭环。系统默认 128 bit 参数已由独立宽拍适配器测试覆盖，但完整渲染、真实 DDR3 访问和显示输出的联合过程仍待验证。[R7][R8]

### 5.5 帧缓冲容量与理论带宽

容量预算按紧密排列的 RGB565 像素计算，每像素占 2 B。640×480 图像的单帧大小为 614400 B，两页合计 1228800 B，即 1.171875 MiB；该值仅包含像素，不包含纹理素材、程序、栈、命令及额外的行对齐间隙。当前默认渲染行缓存为 4096×16 bit，显示 FIFO 为 1024×17 bit，其中第 17 位用于行尾信息。两者的原始存储量与完整帧缓冲不同，仿真中可直接索引的内存数组不代表这些帧数据已被放入片上 RAM。[R7]

设宽度为 $W$、高度为 $H$、每像素字节数为 $b=2$，每秒完整访问次数为 $f$，则单帧字节数和每像素访问一次时的字节流量为：

$$
S_{\mathrm{frame}}=WHb,\qquad B_0=WHbf.
$$

| 60 Hz 扫描读取 | 每显示像素读一次 | 36.864 MB/s | 必要像素流量下界 |
| 扫描加每秒 60 次全屏 Copy | 扫描读、源读、目的写，共三次访问 | 110.592 MB/s | 必要像素流量下界 |
| 扫描加每秒 60 次全屏 Alpha | 扫描读、前景读、背景读、目的写，共四次访问 | 147.456 MB/s | 必要像素流量下界 |
| 扫描加每秒 60 次全屏 Color Key | 当前实现完整读源行与背景行，再写目的行 | 147.456 MB/s | 必要像素流量下界 |

带宽使用十进制 MB/s，只计算有效像素数据。Copy 对每个目的像素增加一次源读和一次写，Alpha 增加前景读、背景读和目的写；当前 Color Key 也读取完整源行与背景行后写回，因此其必要字节流量与 Alpha 相同，并不随透明像素比例自动下降。行级 burst 可以合并请求、减少描述符和切换次数，但不会改变这些像素字节数。表 5-3 中的每秒 60 次全屏操作是预算条件，不是测得的渲染帧率。[R7][R8]

实际外存流量还受到宽拍首尾利用率、刷新、读写换向、命令间隙、仲裁和 CDC 开销影响。当前存储通路采用单 outstanding 事务，持续有效带宽既取决于传输宽度，也取决于从请求发出到响应结束之间的等待；显示 FIFO 能否吸收最坏停顿，还需结合活动扫描阶段的数据消耗速率判断。因此，即使容量和必要流量预算可容纳目标场景，也不能直接推导整机达到 60 FPS。CPU 与硬件的同场景帧时间、实际 DDR 持续带宽、峰值欠载情况和长时间显示稳定性目前均为待实测。[R7]

### 5.6 已有结果的结论范围

现有记录支持的结论是：所列命令与像素定向用例通过，行级读写和 4 KiB 分段在给定边界条件下正确，宽 AXI 适配器覆盖了独立 AW/W 及特定错误恢复场景，小栅格系统完成了控制、换页和扫描交接，Vivado 代理综合能够推断主要块 RAM。这些证据为板级集成提供了可复查的起点，但它们没有覆盖真实 Sapphire 软件、DDR3 训练、异步时钟、HDMI PHY 及固定分辨率下的连续竞争负载。最终性能还需以相同素材、几何尺寸、数值语义和完成边界开展 CPU/硬件对照，不能只统计命令投递时间。[R7][R8][R9]

## 6 板级实现与性能测试

### 6.1 板级工程与配置依据

本系统尚未完成真实 Sapphire、DDR3 控制器与 PHY、HDMI TX/PHY 的集成，也未取得完整工程的布局布线、静态时序和上板测试结果。现有 `c2_renderer_system` 是板卡无关的组装层，能够选择 AXI4-Lite 控制适配和 AXI4 存储适配，但这些选择不会自动生成 CPU、外存物理接口或视频发送器。已有 FPGA 开发工具和软件 IDE 的安装记录，以及 `GUI_HANDOFF.md` 中的配置说明，只提供后续集成的条件和接口依据，不构成 IP 已生成、BSP 已可用或板卡已启动的证明。[R7][R11]

板级配置应以实际竞赛板原理图、器件封装与生成工程共同确定。Sapphire 导出的主接口需要经地址译码及必要的协议桥访问渲染器 CSR，同时与加速器通过系统级互连共享 DDR3；现有渲染器与显示读取器之间的 owner 仲裁并不包含 CPU。生成 IP 后，应逐项核对数据宽度、ID 宽度、时钟域、复位及初始化状态，确认所有响应通道均有真实连接。当前顶层默认的 128 位 AXI 数据宽度和 4 位 ID 宽度属于 RTL 参数，最终值仍须匹配生成端口；软件地址必须来自实际地址分配及 BSP，不能直接沿用行为内存的页基址。[R7][R11]

### 6.2 C 驱动、完成通知与页面所有权

C 驱动的板级版本尚未完成。驱动应使用生成 BSP 中的地址和访问函数，以对齐的 32 位写入准备八个命令字，再提交命令，并把“总线接受提交”“命令执行结束”和“结果可供其他主机访问”作为不同阶段处理。共享帧缓冲需要明确采用不可缓存映射，还是依赖平台提供的缓存维护接口：CPU 生成的源图像及背景数据应在交付硬件前完成必要写回，硬件持有目标页期间不得留下可能再次覆盖结果的 CPU 脏缓存行，CPU 回读前则需处理旧缓存副本。缓存操作、内存屏障及写响应的可见性范围都应由实际 SoC 和互连配置确认，并通过 CPU 写入—硬件读取及硬件写入—CPU 回读两个方向验证，不能预设硬件缓存一致性。【待补充：C 驱动、内存映射属性、缓存维护与跨主机可见性测试。】[R7][R11]

现有状态寄存器还不足以直接构成可靠的逐命令成功通知。`LAST_ERROR` 的有效位直接取自解析器单周期错误脉冲，慢速轮询可能错过该事件；`COMPLETED` 统计引擎完成事件，也包含执行失败的命令，而解析阶段拒绝的命令不会产生相同的引擎完成事件。顶层提供给 CSR 的 `dropped` 又把解析器拒绝计数与 FIFO 的 `in_valid && !in_ready` 周期计数相加，因此正常保持有效的背压等待也会使其增长，不能把它直接当作丢失命令数。驱动验收前须定义可持久读取的完成标识、错误状态与确认方式，明确批次边界、计数回绕及超时处理，并在非法命令、队列满和存储错误条件下检查软件能否结束等待且不误报成功。【待补充：完成/错误通知接口、拒绝与背压统计分离、驱动异常路径及验证记录。】[R7]

页面交接应以所有权转移为准，而不是仅依据活动页号判断。CPU 或渲染器只能写入已经释放给绘制方的页面，全部相关写事务完成并满足跨主机可见性条件后，才能请求显示该页。当前 `flip_ack` 仅为页面控制器内部的提交脉冲，未进入 CSR；请求同一页也会产生提交事件，因此页号不变并不等于请求未完成。反过来，`active_page` 变化也不能独立证明旧页读取已排空：旧显示 reader 在外存长停顿后可能延续到消隐期。待实现的系统契约应分别提供新页提交确认和旧页读事务排空的可观察条件，并规定异常时如何停止访问、清理在途事务和重新分配页面。测试需刻意延迟旧页读响应，在消隐附近提交请求，证明软件不会过早复用仍被读取的旧页。【待补充：换页确认、旧页排空确认、页面所有权状态机及故障恢复测试。】[R7][R11]

### 6.3 DDR3、HDMI 与完整工程验收

DDR3 联调应从厂商生成的校准和固定模式读写例程建立物理接口依据，再接入现有 AXI 适配器。初始化完成前必须保持新内存请求受阻，校准失败应有可观测状态，不允许把初始化输入固定为成功。功能检查应覆盖两页帧缓冲的实际地址范围、字节顺序、不同地址图案、宽拍首尾字节保护、4 KiB 分段及读写切换；对每个已接受写事务，检查对应写响应和随后跨主机回读的一致性。吞吐测量需分别在扫描关闭、扫描开启及 CPU 同时访问的条件下进行，记录有效数据量、测量时间与最长服务间隔。只得到平均带宽仍不足以说明 line FIFO 能承受最坏外存停顿。【待补充：DDR3 校准日志、内存自测、联合访问波形及有效带宽实测。】[R7][R11]

HDMI 验收应直接检查实际发送端和显示设备，目标有效分辨率及刷新要求为 640×480、60 Hz。[R1] 测试画面应包含纯色、RGB565 通道梯度、单像素边界和交替页面标记，以同时检查颜色扩展、坐标对齐和换页撕裂。像素数据与 `de/hsync/vsync` 的流水延迟必须一致，有效显示期间 PHY 还需连续接收像素；显示不应靠暂停光栅等待数据。复位后的首帧黑屏应与后续欠载黑屏区分，检查消隐预取后的第一幅有效画面是否完整，并在渲染与 CPU 存储竞争下观察失锁、条纹、重复页和错误计数。【待补充：HDMI 时序测量、显示设备信息、彩条与双缓冲实拍图片、板卡接线照片。】[R7][R11]

### 6.4 CPU 与硬件加速的对照测量

CPU 与硬件对照需要在输出一致的前提下比较完整绘制耗时。两条路径应使用同一 RGB565 输入、目标尺寸、stride、素材、命令顺序和绘制次数，Alpha 必须采用与现有 RTL 一致的逐通道整数舍入，Color Key 也需具有相同的背景保持语义。每次测试从相同的目标页内容开始，以逐像素回读比较确认结果；在一致性未通过时，不对速度差异作性能结论。CPU 频率、编译器与优化选项、缓存策略、素材是否预装及计时是否包含资源装载均应固定记录，避免把不同工作量或不同缓存状态当作加速效果。【待补充：CPU 参考程序、测试素材、固定随机种子、构建选项和逐像素比对记录。】

## 7 设计特点局限与后续完善

### 7.1 以命令和事务边界组织的工程特点

本设计的特点主要体现在控制、计算和存储之间的责任划分。CPU以矩形为单位提交命令，渲染器执行行级处理，适配器转换存储事务，显示路径按固定光栅消费帧缓冲。命令FIFO缓冲提交节奏，owner仲裁允许显示在渲染存储段之间获得服务；写owner又持续保持到`wr_rsp`被接受，使数据离开行RAM与目的写回完成具有不同含义。上述安排把赛题要求落实为可分别检查的接口契约，已有延迟响应和错误注入用例提供了定向支持。不过，当前没有响应超时机制，事务能够结束仍依赖下游正确返回响应，不能由owner隔离推导出任意故障下均可恢复。[R1][R4][R5][R8]

源行与结果共享一个同步行RAM，体现了存储资源与调度复杂度之间的取舍。Alpha和Color Key先保存源行，再随背景响应逐拍读出源像素并覆盖原位置，避免为前景、背景和结果分别设置完整行缓存；同步读取延迟由背景数据寄存和有效标志配合处理。Vivado代理综合推断出两块RAMB36，支持这一写法能够在所用Artix-7配置下实现块RAM，而不是整行触发器阵列。共享也意味着各处理阶段依序推进，当前结构没有同时缓存下一行源数据与本行输出的双行流水。资源结果因而支持缓存组织的实现判断，尚不足以证明目标Ti60上的最优占用或最高吞吐。[R4][R9]

### 7.2 吞吐限制与数据路径优化方向

当前吞吐限制不仅来自DDR访问速度，也来自共享通路的组织。内部读写均为16位像素拍，渲染器、owner仲裁器与AXI适配器每次只维护一个未结束存储事务；源读、背景读、目的写与显示读不能通过多个在途描述符隐藏彼此的响应等待。外部128位AXI能够聚合多个像素，却仍需通过内部串行通道逐拍装入或拆出，不能解释为端到端每周期处理八个像素。默认16拍burst的有效载荷至多为32字节，对128位AXI而言仍是短突发，遇到行尾或4 KiB边界还会进一步缩短。增加命令FIFO深度只能缓冲提交节奏，不能消除这一数据面瓶颈。[R4][R5][R7]

较长burst可以摊薄请求与响应开销，却也延长一次owner占用，可能使固定光栅的显示读取等待更久；扩大显示FIFO只能吸收有限停顿，不能补足长期平均带宽缺口。因此，burst长度、显示FIFO水位与仲裁策略需要联合评价，不能只观察渲染平均帧时间。若进一步引入宽像素通路、双行缓存或多事务并行，还需补充响应归属、缓存端口分配和读写相关性约束，不能只放宽一个长度参数。第5章给出的像素流量是必要字节数下界，优化效果仍需在CPU竞争、DDR刷新及读写换向存在的完整系统中观察。【待补充：不同burst长度与FIFO配置下的实际有效带宽、最差显示服务间隔、渲染帧时间和资源时序对照。】[R4][R5][R6][R7]

Alpha路径的下一步重点是把既定数值语义与目标器件时序结合。当前计算位于引擎的组合`blend565`函数中，采用RGB565原生通道、统一8位Alpha、偏置128和整数除数255，没有形成已经确认映射到DSP的多级算术流水。官方高阶要求提及DSP或硬件乘法器，现有RTL包含硬件乘加表达式，但Vivado代理的0 DSP只说明该次映射未采用DSP原语，不能单凭这一数字判定混合功能不成立，也不能据此声称目标器件乘法器利用已完成。后续可依据关键路径选择DSP流水、常量除法变换或查找结构，并逐像素保持原有舍入和饱和结果；仅用视觉接近的除以256替代将改变参考语义。【待补充：Ti60算术映射、流水级数、位精确对照及优化前后的时序和资源记录。】[R1][R4][R9]

Color Key的输出语义已经实现透明色位置保留背景，但当前burst路径不是透明像素免访存结构。每行仍读取完整源和背景，并写回完整目的行，因此透明比例变化不会自动降低背景读取量，必要像素流量与当前Alpha路径相同。一条可评估的优化路线是保存源行的透明掩码，通过写字节使能保留命中位置的原背景，从而尝试省去背景行读；另一条路线是按连续非透明区段生成写请求。前者需要贯通掩码到宽AXI首尾字节使能，后者可能因区段碎片化增加事务开销，两者都必须重新检查错误恢复和行边界。颜色键与Alpha当前是独立操作码，融合两种效果还需定义处理顺序，不能通过设置保留flag直接获得。【待补充：颜色键掩码或区段方案、不同透明分布下的访存量及融合效果的像素验证。】[R4][R5][R7]

### 7.3 软件可观察性与页面所有权缺口

第3、4章的寄存器语义表明，当前诊断量尚不能直接承担逐命令成功判定。FIFO的`drop_count`是背压周期数，却与parser拒绝数合并到CSR `0x3c`；`completed_count`包含错误完成，`LAST_ERROR`的valid位也不是黏滞标志。显示侧的`display_underflow`在预取开始时清除，`display_error_count`混合欠载、PHY不就绪、reader错误和行FIFO溢出周期，并非欠载帧数。这些信息有助于定位异常，却不足以计算命令成功率或掉帧比例。软件契约需要区分事件与周期、完成与成功，并提供错误留存和跨域一致快照，才能让第6章的性能与稳定性指标具有可核对口径。【待补充：分类计数、可持久读取的完成/错误状态、快照机制及驱动测试。】[R6][R7]

页面管理需要同时处理正常交付与失败回收。`flip_ack`尚未映射为CSR可读事件，活动页变化也不证明旧页读请求已经排空；若旧reader拖入消隐期，软件立即重用旧页仍可能与显示读取冲突。可靠交接须覆盖新页全部成功写回、必要缓存维护、新页提交及旧页读结束。命令中途错误还可能留下部分已提交结果，当前也不提供任意重叠Copy、自动裁剪或完整表面范围保护，因此失败页不能直接交付显示，提交前仍需软件边界检查。上述限制决定了双缓冲不仅是两个基址轮换，还需要可观察的所有权状态和异常恢复路径。【待补充：换页与旧页排空确认、页面回收、表面边界检查、失败页重绘及超时恢复验证。】[R4][R5][R6][R7]

### 7.4 从板卡无关验证走向完整系统

分层验证有助于定位故障，但不同层次的证据不能互相替代。已有4×2系统仿真采用同源时钟和行为存储，AXI系统shell通过的是DDR尚未初始化时的NOP控制链，Vivado代理资源也不包含真实厂商IP内部；这些记录均不能证明Ti60整机已完成。多时钟集成还需同时保持存储事务顺序、页面请求与确认的一致性以及状态读取完整性，现有只读显示CDC预留接口不能直接用作通用写事务桥。真实Sapphire、DDR3、PLL与HDMI接入后，才能在CPU竞争、长背压和复位扰动下评价固定光栅持续供数能力。【待补充：真实IP与CDC、时钟复位及引脚约束、完整帧闭环、目标器件布局布线和长期稳定性记录。】[R6][R7][R8][R9]

### 7.5 面向高阶挑战的完善路径

官方高阶挑战将Alpha、颜色键去背与高负载互动游戏联系起来，考察启用相关效果时稳定60 FPS下的活动精灵数量。现有算子提供了功能基础，但尚无完整RISC-V游戏与实板负载结果；基础Fill/Copy、burst和双缓冲仍应作为基础验收内容。后续比较需固定素材、精灵尺寸、透明比例、覆盖层数与数值语义，以整帧可交付的写回完成为计时边界，同时报告渲染帧率、显示刷新率、平均与最差帧时间及分类异常计数。只有定位算术、内部传输或DDR等待的实际瓶颈，才能决定哪些优化值得投入，而不能预设加速倍数、稳定精灵上限或竞赛得分。【待补充：同场景CPU/硬件对照、启用Alpha与Color Key的互动演示、稳定60 FPS负载边界及原始记录。】[R1][R7][R8]

## 8 总结

本文围绕赛题二构建了板卡无关的二维渲染协处理器及系统组装框架。设计采用矩形命令划分处理器与硬件的职责，以固定256位描述符表达绘制操作，通过命令FIFO和解析校验进入按行执行的渲染引擎。源行与运算结果复用同步行RAM，读写请求依据突发上限和4 KiB边界拆分；带owner的仲裁器把写描述符、写数据及写响应保持为同一事务，宽AXI适配器承担内部RGB565像素与外部总线数据之间的转换。显示路径在垂直消隐提交页面，并通过预取和行FIFO对接固定光栅。上述方法形成了从命令输入、像素处理、存储提交到扫描输出的可检查接口关系。[R3][R4][R5][R6][R7]

已有10项功能回归与11项展开记录覆盖了所列命令、边界、背压和异常场景，Vivado代理综合也推断出渲染行RAM及显示FIFO的块存储实现。结论仍限于对应的RTL、行为模型和代理工程：4×2扫描测试不是目标分辨率的板级验证，NOP系统壳测试没有验证AXI帧缓冲数据通路，Ti60结构探针的逻辑裁剪也使其不能代表完整SoC资源。当前尚无CPU/硬件渲染加速比、实际高负载帧率或完整工程时序的测量结论。[R8][R9][R10]

整机实现需要把真实Sapphire、DDR3与HDMI、系统互连、时钟复位和CDC接入现有接口，并补齐驱动可观察的完成/错误与页面交接契约。在此基础上，通过同场景像素一致性和完整绘制耗时评价性能，再依据存储等待、显示欠载和关键路径决定突发长度、缓存组织及Alpha运算优化。高阶目标应由启用Alpha与Color Key的交互游戏及可重复的负载测试支持，不能由算子存在或显示刷新率代替。现阶段成果提供了可继续集成的RTL基础及证据边界，完整比赛系统的完成度仍取决于这些后续验证。[R1][R7][R11]

| 0x30 | ACCEPTED | 读 | parser消费的命令数，包含随后被判为非法的命令 |
| 0x34 | COMPLETED | 读 | engine产生完成事件的次数，包含错误完成 |
| 0x38 | MEM_ERR | 读 | parser统计的engine错误完成次数；名称不意味着仅DDR物理错误 |
| 0x3C | DROPPED | 读 | parser拒绝数与FIFO诊断计数之和，不能直接解释为丢失命令条数 |
| 0x40 | REQ_COUNT | 读 | 渲染引擎抽象存储请求计数，不是整机全部AXI请求数 |
| 0x44 | PIXEL_COUNT | 读 | 渲染引擎像素数据阶段计数，不是成功提交的帧数 |
| 0x48 | DISP_PIXELS | 读 | 显示路径像素计数 |
| 0x4C | DISP_ERRORS | 读 | 显示路径累计错误计数 |
| 0x50 | MEM_READS | 读 | 当前渲染/显示存储路径的读请求计数 |
| 0x54 | MEM_WRITES | 读 | 当前渲染/显示存储路径的写请求计数 |
| 0x58 | MEM_RSP | 读 | 仲裁器读响应beat计数，不包含独立AXI B写完成次数 |
| 0x5C | LAST_ERROR | 读 | parser错误有效脉冲、错误码和截断后的序号 |

`STATUS`的bit0—8依次对应命令FIFO满、parser忙、engine忙、display忙、显示欠载、存储错误状态、页控制器pending、命令提交pending和页面提交pending；bit15:9为FIFO占用量的低7位。默认双页配置下，`PAGE_STATUS`的bit0为活动页，bit8为待切换页，bit16为页控制器pending。命令被CSR接收、进入FIFO、经parser消费、被engine执行和写完成是不同事件，软件不能只用一个计数器代替完整生命周期判断。[R3][R7]

`LAST_ERROR`的bit0直接反映单周期`parser_error_valid`，bit7:4为保留的错误码，bit31:8为错误命令序号低24位；当前不是读清的黏滞错误有效位。错误码0—5分别表示无错误、非法操作码、非法像素格式、非法尺寸、非法stride和地址未对齐。`DROPPED`中的FIFO计数在每拍`in_valid && !in_ready`时增长，而提交槽会在背压期间保持valid，因此合法等待也可能被计入。稳健驱动需要补齐明确的完成、拒绝和超时判定契约，不能从这些混合量直接计算成功率。[R3][R7]

### A.3 存储握手约定

抽象请求的`req_addr`是字节地址，`req_len=N-1`表示N个16位像素beat。读数据通过有序`rsp_*`返回；写请求接受后，通过独立`wr_*`输送数据，末拍标记`wr_last`，并通过`wr_rsp_*`返回提交结果。写数据结束与写完成不能合并，当前宽AXI适配器将B通道映射为写完成响应。任一有效通道在背压期间应保持有效及负载稳定，错误恢复仍依赖下游最终结束已接受的事务；当前没有无限停顿下的超时收敛保证。[R4][R5]
